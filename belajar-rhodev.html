01 · Konteks

Pahami sistemnya dulu

Ada tiga aplikasi di folder app, dan satu database MySQL rhodev_island_logistic (diisi dari create+insert.sql lewat phpMyAdmin).

desktopTauri 2: UI React + backend RustDispatcher, CourierHalaman Dispatcher (assign courier) dan Courier (pick up, deliver)
server-dashboardReact + axiosDispatcher (monitoring)Peta Terra, event log, activity log (sudah ada panelnya, isinya kosong karena belum ada yang mencatat)

Server pakai arsitektur hexagonal (ports & adapters)

Nama foldernya menjelaskan perannya. Hafalkan, karena bug trait dan import ada di sini.

Kenapa pakai trait? Supaya server.rs cuma tahu "ada sesuatu yang punya method dispatch_operator", tanpa peduli implementasinya. Konsekuensinya: method yang tidak ditulis di trait tidak bisa dipanggil dari handler. Itu bug trait.

Siklus status order item

Hal lain yang perlu kamu tahu dari database:

  • Operator punya role_id: 1 = Dispatcher, 2 = Courier. Dispatcher dan Courier sama-sama baris di tabel operator.
  • Operator punya dua relasi ke Region: place_of_birth (wajib) dan region_specialty_id (boleh NULL). Spesialisasi inilah yang dipakai fitur rekomendasi.
  • Medicine dibuat oleh satu Manufacturer. Jadi lokasi pickup order item = posisi manufacturer obatnya; tujuan = warehouse milik order.
  • WarehouseInventory punya primary key gabungan (warehouse_id, medicine_id): tabel penghubung many-to-many antara Warehouse dan Medicine, plus kolom quantity dan reorder_threshold.
  • activity_log berdiri sendiri (tidak ada foreign key), dengan timestamp DEFAULT CURRENT_TIMESTAMP.

# 3. Desktop (terminal lain)
cd app/desktop && npm install && npm run tauri dev

cd app/server-dashboard && npm install && npm run dev

Use case diagram

Use case diagram menjawab satu pertanyaan: siapa memakai sistem untuk mencapai tujuan apa. Bukan urutan langkah, bukan tombol.

Teori: elemen dan aturannya

ElemenNotasiAturan
ActorStick figure, nama kata bendaPeran (bukan orang tertentu), selalu di luar system boundary. Kiri: aktor yang benar-benar ada di sistem dan menjalankan use case sendiri (punya halaman, command, atau role di database). Kanan: pihak eksternal yang disebut di soal, tidak punya halaman, tapi terlibat langsung di sebuah use case (datanya dipakai atau diubah).

Aturan case maker untuk soal ini. (1) Tidak ada «extend». (2) Aktor di kiri = aktor yang benar-benar ada di dalam sistem. (3) Aktor di kanan = pihak eksternal yang terhubung langsung ke use case. Panah include menunjuk ke use case yang dipakai (Dispatch Courier → Record Activity Log).

Cara menemukan aktor hanya dari kode

Kode tidak punya daftar "aktor". Yang ada adalah pintu masuk: halaman, command, prefix route, dan role di database. Aktor adalah siapa pun yang berdiri di depan pintu itu. Jalankan lima pertanyaan ini berurutan:

  1. Siapa yang disebut di kode? Cari tabel role (isinya (1,'Dispatcher'), (2,'Courier')), tipe Role = "Dispatcher" | "Courier" di desktop/src/model/operator.ts, nama file dispatcher_controller.rs / courier_controller.rs, prefix router /dispatcher, /courier, /warehouse, /manufacturer, plus empat pihak di teks soal.
  2. Dia menekan tombol sendiri? Kalau ada halaman atau command yang dia jalankan (DispatcherPage, CourierPage, invoke("dispatch_operator")), dia aktor kiri.
  3. Kalau tidak menekan apa-apa, apakah dia terlibat langsung di satu use case? Datanya dipakai atau diubah oleh use case itu, tapi dia tidak punya pintu. Itu aktor kanan. Kalau tidak terlibat langsung, jangan digambar.
  4. Dia pihak, atau cuma benda? Coba jadikan subjek kalimat. "Manufacturer memproduksi obat" masuk akal, jadi pihak. "Medicine ..." tidak bisa melakukan apa-apa; obat itu yang diproduksi dan diantar, jadi objek (masuk class diagram), bukan aktor. Punya tabel atau DTO tidak otomatis jadi aktor. Warehouse itu tempat; yang bertindak adalah Warehouse Operator.
  5. Bisa kamu tunjuk baris kodenya? Kalau tidak, buang. Itu sebabnya Supervisor dari versi lama dihapus: kata itu tidak ada di kode mana pun.

Dashboard tidak punya login, jadi lihat route yang ia panggil. get-event-log dan get-activity-log didaftarkan di dispatcher_router, dan desktop juga punya dispatcher_controller::get_event_log / get_activity_log. Cara menemukan use case hanya dari kode

  1. Kumpulkan semua pintu masuk. .route(...) di adapter/inbound/server.rs, generate_handler![...] di src-tauri/src/lib.rs, invoke(...) di desktop/src/pages, api.get(...) di server-dashboard/src/services/data.service.ts. Untuk aktor kanan yang tidak punya pintu, ikuti status order di service.rs (lihat tabel di bawah).

  3. Satu tujuan aktor = satu use case. POST biasanya aksi (dispatch-operator → Dispatch Courier). GET yang mengisi layar jadi "View ...". Endpoint pembantu digabung ke use case yang memakainya: get-operator-list mengisi dropdown, warehouse list dan manufacturer list cuma marker di Terra Map, refresh_data itu poller teknis.

  5. if di dalam fungsi bukan use case. Cek quantity > reorder_threshold di restock_warehouse cukup jadi decision di activity diagram.
  6. Beri nama kata kerja + objek, pakai bahasa bisnis, bukan nama fungsi (Deliver Medicine, bukan complete_task).

Kenapa digambar begini

  • Tidak ada extendSesuai aturan case maker. Rekomendasi jadi use case sendiri milik Dispatcher. Restock jadi use case milik Warehouse Operator; syarat threshold pindah ke activity diagram.
  • Kiri hanya aktor internalDispatcher dan Courier punya role di tabel role, halaman, dan command sendiri. Operator jadi parent karena keduanya baris di tabel operator dan sama-sama bisa ganti profil.
  • Kanan hanya pihak eksternal dari soalManufacturer terhubung ke Produce Medicine Batch. Warehouse Operator ke Request Medicine Restock dan Update Warehouse Stock. Keduanya tidak punya halaman, jadi tidak boleh di kiri. Timer simulasi tidak digambar sebagai aktor.
  • Dashboard dipakai DispatcherRoute log ada di dispatcher_router. Ini bisa kamu tunjuk saat presentasi, beda dengan Supervisor yang dulu cuma tebakan.
  • Record Activity Log di-includeSoal minta "records every action performed by an operator". Fitur ini dipanggil di setiap dispatch, pick up, dan deliver, jadi include. Tidak punya aktor karena tidak ada orang yang menjalankannya langsung.
  • Use case yang dibuangView Warehouse Inventory (endpoint tanpa pemanggil), View Warehouse List dan View Manufacturer (cuma marker di Terra Map), View Courier List (sudah tercakup oleh rekomendasi).
Kesalahan yang sering dipotong nilainya. Panah di garis association; aktor di dalam boundary; nama use case berupa tombol atau layar ("Courier Page"); arah include terbalik; masih ada «extend»; aktor eksternal di kiri atau aktor tanpa bukti kode; urutan langkah (1, 2, 3) digambar dengan include berantai; use case yang tidak punya aktor maupun relasi include/extend.

Activity diagram

Activity diagram menggambar alur kerja satu use case: langkah apa, oleh siapa, cabang ke mana kalau gagal. Ini flowchart versi UML dengan swimlane.

Teori notasi

NotasiBentukAturan
Initial nodeLingkaran hitam penuhTepat satu per diagram (per activity).
Activity finalLingkaran hitam dalam lingkaran (bullseye)Akhir seluruh alur. Boleh lebih dari satu, tapi lebih rapi satu lewat merge.
ActionPersegi sudut tumpulKata kerja aktif: "Send pickup request", "Record activity log".
DecisionBelah ketupat, 1 masuk banyak keluarSetiap panah keluar wajib punya guard dalam kurung siku: [found] / [else]. Guard harus saling lepas dan lengkap.
MergeBelah ketupat, banyak masuk 1 keluarMenyatukan cabang alternatif. Tanpa guard.
Fork / joinBar hitam tebalFork memecah jadi alur paralel; join menunggu semuanya selesai. Jangan dipakai untuk pilihan (itu decision).
Swimlane (partition)Kolom berjudulSiapa yang melakukan action. Rubrik "identify actor(s)" melihat ini.
Control flowPanahArah alur. Semua node harus tersambung; tidak ada action yang buntu.

Kenapa digambar begini

  • Tiga swimlaneAktor manusia (Courier / Dispatcher), Desktop App, dan Server. Desktop dan Server dipisah karena memang dua program; validasi Tauri terjadi di desktop, validasi bisnis di server. Kalau digabung jadi "System", penguji tidak bisa melihat di mana bug Tauri berada.
  • Guard menyalin kode[status = ASSIGNED] karena kode mengecek order_item.status != 4; [distance ≤ 20 unit] karena ARRIVAL_RADIUS = 20.0. Menyalin aturan nyata membuat alur "complete and reasonable".
  • Semua cabang gagal bertemu di mergeDaripada empat final node, semua error masuk merge → "Return error status code" → kembali ke desktop. Satu jalur keluar lebih mudah dibaca dan tetap benar.
  • Desktop memeriksa responsSetelah server menjawab, desktop yang menentukan pesan sukses atau error (setMessage). Tanpa langkah ini alur berhenti di server dan aktor tidak pernah tahu hasilnya.
  • Record activity log setelah updateLog hanya dicatat kalau aksi berhasil. Mencatat sebelum update bisa menghasilkan log aksi yang ternyata gagal.
  • Update di dispatch berurutanKode meng-update operator dulu, baru order item (repository.rs), jadi digambar berurutan, bukan fork/join. Fork/join hanya untuk langkah yang benar-benar jalan paralel.
  • Dua panah ke "Show error message" lewat mergeError dari validasi Tauri ([ids ≤ 0]) dan error dari server sama-sama berakhir di pesan error. Keduanya digabung dulu di merge, baru masuk ke action, supaya tidak ada action dengan dua panah masuk.
  • Final node di lane aktorAlur baru selesai setelah aktor (Courier / Dispatcher) melihat pesan hasil, jadi "View result message" dan final node ada di lane aktor.
Kesalahan umum. Decision tanpa guard; dua panah masuk langsung ke satu action tanpa merge (sebagian penguji memotong); action ditaruh di lane yang salah (contoh: "Validate distance" di lane Courier); diagram berhenti tanpa final node; nama action berupa kata benda ("Pickup").

Multi-layer sequence diagram

Sequence diagram menunjukkan objek mana mengirim pesan ke objek mana, dalam urutan waktu dari atas ke bawah. "Multi-layer" berarti objeknya dikelompokkan per lapisan: boundary, control, entity.

Teori: lapisan objek (BCE)

LayerIkonArtinyaDi aplikasi ini
ActorStick figurePemicu dari luarCourier, Dispatcher
BoundaryLingkaran dengan garis tegak di kiriAntarmuka: tempat input masuk / output keluarCourierPage, DispatcherPage (React), Server (handler axum, pintu masuk server)
ControlLingkaran dengan panah melingkarLogika, koordinasi, aturanCourierController (command Tauri), ApiClient, Service, Repository
EntityLingkaran bergaris bawahData yang disimpanOrderItem, Operator, ActivityLog (model SeaORM = tabel)

Aturan layer: aktor hanya bicara ke boundary; boundary ke control; control ke control / entity. Entity tidak memanggil boundary. Kalau panahmu lompat dari aktor langsung ke entity, layer-nya salah.

Teori: pesan, aktivasi, fragment

Synchronous message (input)Garis penuh, kepala panah penuhPemanggilan method / request; pengirim menunggu. Tulis nama method + parameter.

Kenapa digambar begini

  • Urutan lifeline = urutan lapisanKiri ke kanan: aktor → boundary → control → entity. Setiap lifeline adalah file nyata: CourierPage.tsx, courier_controller.rs, api_client.rs, server.rs, service.rs, repository.rs, entity/order_item.rs. Ini menjawab "identify object(s) layer".
  • Nama pesan = nama fungsipickup_medicine(op_id, item_id), get_order_item(item_id), find_operator(op_id) persis seperti di kode. Penguji gampang mencocokkan, dan kamu gampang menjelaskan saat presentasi.
  • Setiap call punya returnRubrik "input message" dan "output message" punya bobot sama besar (4). Return ditulis dengan tipe nyata: OrderItemModelEx, Ok(()), Err(404 / 403 / 400 / 409).

06 · Bekal kode

Rust kilat untuk soal ini

Kamu tidak perlu jago Rust. Cukup lima konsep ini, karena setiap bug berasal dari salah satunya.

1. Module dan use

File Rust tidak otomatis jadi bagian program. File harus didaftarkan dengan pub mod nama; di file induknya (entity.rs atau entity/mod.rs, jangan dua-duanya). Setelah terdaftar, tipe dari file lain dipakai lewat use crate::path::Tipe;.

rust
// core/domain/entity/mod.rs  -> mendaftarkan file operator.rs
pub mod operator;

// service.rs  -> mengimpor tipe agar bisa dipakai dengan nama pendek
use crate::core::domain::entity::operator::ActiveModel as OperatorActiveModel;

Pesan error khasnya: E0432 unresolved import, E0433 cannot find `x` in `super`, E0425 cannot find type.

2. Trait

Trait = daftar method yang wajib dimiliki sebuah tipe (seperti interface di Java). impl ServiceTrait for Service hanya boleh berisi method yang tertulis di trait. Kalau ada method ekstra, error E0407 method is not a member of trait; pemanggil lewat trait dapat E0599 no method named .... Method helper yang bukan bagian kontrak ditulis di blok terpisah impl<R> Service<R> { ... }.

3. async / await

Fungsi async tidak langsung jalan; ia mengembalikan Future (janji hasil). Hasil baru keluar setelah .await. Lupa .await berarti kamu memegang Future, bukan Result, sehingga match ... { Ok(..) } gagal dengan E0308 mismatched types ... found impl Future.

4. Ownership, borrowing, mut

Variabel Rust default-nya tidak bisa diubah. vec.push(x) butuh pinjaman mutable (&mut vec), jadi variabelnya harus let mut. Error: E0596 cannot borrow as mutable. Konsep ownership lain yang muncul di kode: into_option() memindahkan (move) field keluar dari struct; setelah itu field tersebut tidak bisa dipakai lagi, tapi field lain (yang Copy seperti i32) masih bisa.

5. SeaORM: Model vs ActiveModel

TipeUntuk
ModelHasil SELECT, data read-only.
ModelExModel + relasi yang di-load (.with(Medicine)).
ActiveModelUntuk INSERT / UPDATE. Setiap field berupa ActiveValue.
ActiveValue::Set(v)Kolom ini ditulis ke database.
ActiveValue::Unchanged(v)Dipakai sebagai kunci (WHERE id = v), tidak di-update.
NotSet (dari ..Default::default())Kolom tidak disentuh. Di INSERT, database pakai DEFAULT / auto increment.
rust
let operator_active = OperatorActiveModel {
    id: ActiveValue::Unchanged(operator_id),   // WHERE id = operator_id
    availability: ActiveValue::Set(0),          // SET availability = 0
    ..Default::default()                        // kolom lain NotSet: tidak diubah
};
operator_active.update(&tx).await?;             // UPDATE operator SET availability = 0 WHERE id = ?

Kalau field lupa di-Set, kodenya tetap compile dan jalan, tapi kolomnya tidak berubah. Ini bug paling licin karena tidak ada error.

INSERT vs UPDATE

UPDATEINSERT

Contohdispatch_operator, pickup_medicinerestock_warehouse → create_order, record_activity

Struct ActiveModel dibuat otomatis oleh macro DeriveEntityModel di file entity, lalu diberi nama panggilan lewat use ...::ActiveModel as OperatorActiveModel di atas file. Satu formulir dipakai pakai variabel biasa; banyak formulir dikumpulkan di Vec dengan .push(...).

Model gunanya apa kalau tidak menyimpan? Untuk dibaca: mengecek (if operator.availability != 1), menghitung (jarak), dirakit jadi DTO untuk layar, dan jadi bahan nilai baru (completed_job_count + 1) yang lalu disimpan lewat ActiveModel. Tiap request SELECT ulang, jadi tidak ada data basi.

6. Result, Option, dan unwrap

KotakIsiContoh
Result<T, E>Ok(data) atau Err(error): hasil yang bisa gagalfind_operator(...)
Option<T>Some(data) atau None: data yang bisa kosongcourier_id: Option<i32>, hasil .one()

.unwrap() membuka kotak dan mengambil isinya; kalau isinya Err/None, program panic. Di service selalu dicek dulu (if ... is_err() { return Err(...) }), baru di-unwrap. Cara lain: match, if let Some(x), ? (langsung return error), .unwrap_or_default() (isi kosong kalau tidak ada).

Fungsi yang berjanji -> Result<...> harus mengembalikan Result di semua jalan. Setelah semua if ... return Err, baris terakhir Ok(()) tanpa titik koma. Lupa → E0317 if may be missing an else clause.

7. Pinjam dengan .iter(), salin dengan .clone()

for x in list mengambil (move) list sampai habis. for x in list.iter() hanya meminjam, list tetap utuh untuk dipakai lagi. Barang pinjaman boleh dilihat tapi tidak boleh dibongkar (into_option() membongkar), jadi buat salinan milik sendiri dengan .clone(). Error khasnya: E0382 use of moved value dan E0507 cannot move out of ... behind a shared reference.

Tauri dan React dalam satu kalimat

React memanggil invoke("pickup_medicine", { operator_id, order_item_id }); Tauri mencari fungsi Rust bertanda #[tauri::command] dengan nama itu (didaftarkan di generate_handler! di lib.rs) dan mengisi parameternya dari object tadi. rename_all = "snake_case" membuat nama key di JS harus snake_case.

  • Tiru Event LogPola yang sudah ada di kode lebih mudah dipertahankan di depan penguji: "saya mengikuti cara case maker mencatat event".
  • Masuk ServiceTraitKarena record_activity ditulis di dalam impl ServiceTrait, ia harus didaftarkan di trait (pelajaran bug trait, E0407). Alternatifnya helper di blok impl Service<R> terpisah tanpa trait; dua-duanya benar.

  • Gagal log → 500Sama seperti error database lain di fungsi itu. Catatan: aksinya sudah tersimpan, jadi kalau ditanya, kamu bisa sebut alternatifnya (cukup eprintln! tanpa membatalkan respons).
  • Teks log jelasPakai codename, bukan angka id, dan kata kerja yang sesuai aksinya. "5 pick up order item #12" untuk aksi dispatch itu menyesatkan.

B. Courier recommendation (sort feature) BELUM

Teori weighted scoring. Beberapa kriteria dengan satuan berbeda dijadikan satu angka. Langkahnya: (1) ubah tiap kriteria ke skala sama 0 sampai 1 (normalisasi), (2) kalikan dengan bobot yang jumlahnya 1, (3) jumlahkan, (4) urutkan dari terbesar.

rumus
distanceScore  = 1 − jarak(courier, manufacturer) / jarakTerjauh     (dekat → mendekati 1)
specialtyScore = 1 jika region_specialty courier = region manufacturer, selain itu 0
score          = 0.7 × distanceScore + 0.3 × specialtyScore

Kenapa 0.7 dan 0.3? Jarak langsung menentukan waktu tempuh dan courier harus sampai dalam radius 20 unit sebelum bisa pick up, jadi lebih penting. Spesialisasi jadi pembeda di antara courier yang jaraknya mirip. Bobotnya pilihan desain: kamu boleh pakai angka lain asal bisa menjelaskan.
